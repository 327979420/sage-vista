# 01｜规则治理与改动流程

版本：`1.3.0`
最后更新：2026-08-30

## 本文件负责

文档权威、版本、批准状态和从规则到生产的固定流程。不负责具体评分或交易参数。

## 权威顺序

对应模块规则 → 总手册 → 决策日志 → 注册表 / 实验账本 / 版本产物 → 代码与测试 → UI → 聊天。

## 语义改动固定流程

1. 先把用户意图写入 `docs/CHANGE_REQUESTS_ZH.md`。碎片想法标为 `captured`，明确获准执行后才变为 `approved`。
2. 修改受影响模块的规则、版本和变更记录；这一步必须发生在代码编辑之前。
3. 在 `docs/DECISION_LOG_ZH.md` 追加日期、理由、范围和状态。
4. 影响选股、排序、持仓或退出时，按 `08_BACKTEST_AND_EXPERIMENTS.md` 预登记。
5. 修改共享底层代码，禁止另建平行口径。
6. 运行单元、防前视、数据契约和网页测试。
7. 分块回测并保存断点；永久保存成功、失败和中断结果。
8. 证据足够后才升级正式权重和 UI 结论。
9. 发布、核对线上版本与数据日期，并把测试、提交、网站证据写回需求账本后，再报告用户。

## 架构评审闸门

任何代码、数据合约、扫描、策略、实验、工作流、网站行为或Discord行为的修改，都必须先按`docs/CHANGE_WORKFLOW_ZH.md`提交设计包。设计包必须说明当前链路、目标插入点、唯一负责模块、输入输出、影响与不影响范围、历史兼容、测试、人工案例、回退方式和不超过20分钟的工作包。

- 提出需求不等于批准实施；Codex在需求进入的同一阶段不得直接编辑业务代码。
- 设计包状态为`design_review`。只有用户看过设计包并明确说“按这个方案做”“批准实施”或“开始执行对应CR”，才能进入`approved`／`implementing`。
- 用户修改范围后，旧批准失效；必须更新设计包并重新确认。
- 实施中需要触碰设计包外模块、改变未登记输出或扩大为多模块工作时，立即停止并退回`design_review`，禁止“顺便改”。
- 只读诊断和治理／设计文档可以在批准前完成；紧急生产修复仍需最小影响卡和用户授权。

这道闸门高于“先规则后代码”：先完成并批准架构设计，再更新模块规则，最后才允许代码实现。

## 团队式交付阶段

固定阶段为：`captured → design_review → approved → implementing → verified → implemented`。研究请求在批准后可以进入`experimental`，但实验结论仍须另行批准才能改变生产。

- 产品负责人（用户）批准目标、架构、验收与上线。
- Codex先承担架构／研究职责，获批后才切换为实现职责。
- 测试与CI只证明契约和实现，不代替用户判断是否实用。
- Git提交、部署和Discord发送都是独立发布动作，不得从“本地完成”自动推断授权。
- 每个CR拆成可独立验收的小包；预计超过20分钟先拆分，完成一包就报告差异和下一包边界。

## 碎片需求怎样归档

- 用户提出但尚未要求实施的想法：只进入需求账本，状态为 `captured`，不得直接改变生产。
- 用户明确批准、且机器定义足够的改动：状态改为 `approved`，先更新对应模块规则，再开始代码。
- 需要数据验证的策略想法：同时预登记实验，状态为 `experimental`；实验结束前不能冒充正式规则。
- 纯修错、重构或性能优化：需求账本先记录问题、范围和“不改变业务语义”；若实际会改变用户看到的结果，必须升级为语义改动流程。
- 每条需求必须能追溯到负责模块、规则版本、代码 / 数据产物、测试、提交和生产验证；暂缓或否决也保留原因。

## 新对话接手规则

- 新对话先读 `docs/NEXT_SESSION_HANDOFF_ZH.md`、`docs/CURRENT_STATUS_ZH.md`、总手册和唯一受影响模块，不把旧聊天当权威事实。
- 当前日期、生产收盘日、回测断点、模型 / 因子版本和待运行实验从机器状态生成；交接文档不得手抄这些数字后长期不更新。
- 新对话第一轮先复述当前事实、任务范围和不会触碰的边界；没有得到用户的新任务时，不自行启动已排队但未批准的策略改动。

安全或未来数据问题可以先暂停生产，但恢复前必须补文档与测试。

## 状态标签

- `current`：当前代码和生产都已实现。
- `approved_target`：规则已批准，但尚未完整实现或验证。
- `experimental`：只允许研究、归因或同分比较。
- `validated`：达到预登记标准并获准进入正式模型。
- `retired`：停止用于新结果，但历史记录永久保留。

任何文档必须区分这些状态。禁止把目标或排队任务写成“已完成”。

## 版本规则

- 模块内部参数变化：只升级该模块版本。
- 模块职责或全局流程变化：同时升级总手册。
- 因子库、评分模型、执行模型、实验、UI 和数据快照分别有版本。
- 历史信号保留当时版本，不用新规则重写旧分。

## 仓库瘦身与可读性

- 文件年龄只能提示复核，不能单独证明文件无用。删除前必须同时检查运行入口、模块引用、工作流、测试、文档链接和实验账本。
- 正式网站目录只保存四个产品入口实际需要的静态资产与生产JSON。只用于复现实验的结果移入`research/`，避免随每次网站构建和发布重复携带。
- 已完成、失败、负结果、样本不足和中断实验属于永久证据，不因页面退役而删除；真正无消费者、无实验引用且可由Git历史恢复的原型才允许移除。
- 旧项目名只允许存在于不可改写的历史记录或会影响既有实验复现的冻结标识中；当前代码、环境变量、数据库默认名和说明文字统一使用Sage Vista。
- 面向维护者的Python入口必须用模块说明写清职责、主要输入、主要输出和安全边界。注释解释“为什么”与阶段边界，不逐行复述语法，也不保留已经失效的注释。
- 新增中间产物默认写入被Git忽略的`work/`或临时目录；只有生产页面依赖或必须版本化的研究证据才能进入`public/`或`research/`。

## 联动条件

治理规则改变时联动总手册和根目录 `AGENTS.md`。普通单模块改动无需修改本文件。
